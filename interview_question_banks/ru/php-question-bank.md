# Часть A. Ядро PHP (теория)

## A1. Язык, типы, операторы

**A1.1. Что такое PHP и его основные возможности?** [S1]
- Открытый серверный скриптовый язык, созданный прежде всего для веб-разработки: обрабатывает запрос на сервере, генерирует динамические страницы, работает с БД.
- Возможности: простота, кроссплатформенность, поддержка ООП, сессии, обширные библиотеки, множество фреймворков, лёгкая интеграция с HTML.

**A1.2. Переменные и динамическая типизация.** [S1]
- Переменная начинается с `$`; тип определяется присвоенным значением (динамическая типизация). Отсюда же — ловушка нестрогого сравнения (A1.3).

**A1.3. Разница между `==` и `===`.** [S1] 🪤
- `==` сравнивает значения **после приведения типов**; `===` — значение **и тип** без приведения.
```php
var_dump(1 == "1");   // true  — приведение типов
var_dump(1 === "1");  // false — разные типы
```
- 💡 Строгое сравнение делает код предсказуемым — на собеседованиях это ценят.
- ⚠️ **PHP 8 — сравнение числа и строки поменяли** (RFC «Saner string to number comparisons»): число vs **нечисловая** строка теперь сравнивается как строки — `0 == "abc"` → **false** (в PHP 7 было true), `0 == ""` → false. Числовые строки — как раньше: `42 == " 42"` → true. Тот же баг жил в `in_array(0, ["foo"])`: PHP 7 — true, PHP 8 — false.
- 🧠 **Механизм:** в PHP 7 строка в нестрогом сравнении кастовалась в число — любая нечисловая давала 0, отсюда `0 == "abc"` → true. В PHP 8 при нечисловой строке — наоборот: кастуется число в строку, и сравниваются строки; числовые строки сравниваются как числа, как и раньше.

**A1.4. `strlen` vs `mb_strlen`.** [S4] 🪤
- `strlen()` считает **байты**, `mb_strlen()` — **символы**. Для кириллицы в UTF-8 разница вдвое.
```php
strlen('Вася');    // 8 — байты (4 символа × 2 байта)
mb_strlen('Вася'); // 4 — символы
```
- ⚠️ Кандидат в S4 ответил «4» — перепутал байты с символами.

**A1.5. Аргументы функции — по значению или по ссылке?** [S3]
- По умолчанию всё, **кроме объектов, — по значению**; **объекты — всегда по ссылке**.
- Принудительная передача по ссылке — знак `&` в сигнатуре.
- Массивы — по значению, но под капотом **copy-on-write (COW)**: передаётся ссылка на тот же zval, копия происходит только при изменении (экономия памяти на больших массивах).
- 💡 Упоминание COW — сильный момент ответа.

**A1.6. `include` vs `require` (и `_once`-варианты).** [S1]
- Оба подключают файл; разница в поведении при отсутствии файла: `include` — **warning** и скрипт продолжает; `require` — **fatal error** и остановка.
- `include_once`/`require_once` гарантируют **однократное** подключение (защита от повторного объявления функций/классов).
- `require` — для обязательных файлов, `include` — для опциональных.

**A1.7. Генераторы vs итераторы.** [S4]
- Генератор — функция с `yield`, сохраняющая состояние между вызовами; возвращает объект `Generator`, реализующий интерфейс `Iterator` (`current`, `next`, `key`, `rewind`, `valid`).
- Применение: читать миллионы строк из БД **батчами/чанками** (`chunk()` в Laravel) — экономия памяти, данные грузятся порциями.
- Итератор — интерфейс PHP и одноимённый паттерн; `foreach` работает через него; кастомный класс можно подписать на `Iterator` и использовать в `foreach`.
- 💡 `yield` — ленивая (поштучная) обработка больших выборок без загрузки всего в память.

## A2. Строки и массивы

**A2.1. Массивы в PHP.** [S1]
- Хранят множество значений в одной переменной; три вида: **индексированные, ассоциативные, многомерные**. Упрощают циклы, поиск, сортировку.

**A2.2. Одинарные vs двойные кавычки.** [S3]
- Двойные кавычки PHP **парсит содержимое** (интерполяция переменных) → чуть медленнее; одинарные — нет.
- 💡 Мелочь уровня code review: в строках без подстановок использовать одинарные.

**A2.3. Мапа-ключ в PHP; канонический ключ для группировки.** [✍️] 🔧
- Ассоциативный массив PHP - это и есть хеш-таблица; ключи - **только int | string**, массив в ключ нельзя (Illegal offset type). Составную подпись (аналог Go `[26]int`) нужно **сериализовать в строку самому**.
- Группировка анаграмм, вариант 1 (сортировка букв): `$chars = str_split($str); sort($chars); $key = implode('', $chars);` - «eat»/«tea»/«ate» → `aet`, O(n·k log k).
- Вариант 2 (счётчик, O(n·k)): `$counts = array_fill(0, 26, 0);` … `$counts[ord($str[$i]) - ord('a')]++;` … `$key = implode(',', $counts);` - запятые разделяют 26 чисел, сериализация однозначна.
- Идиома наполнения: `$groups[$key][] = $str;` (ключа нет - массив создаётся сам), в конце `array_values($groups)`.
- Ближе всего к `[26]int`: ключ = `pack('C*', ...$counts)` - фиксированная 26-байтовая строка (счётчики ≤ 255). Плюшка PHP: `count_chars($str, 1)` сразу отдаёт [код_байта => частота] (потом ksort + сериализация).
- 🧠 **Механизм:** в Go массивы/структуры сравнимы по значению, рантайм сам считает по ним хеш → подпись идёт в ключ как есть. PHP хеширует только int|string, поэтому шаг сериализации делает программист. Приём один и тот же: нормализуй элемент (sort - порядок букв; count - вектор частот) → одинаковые подписи → один бакет.

## A3. ООП

**A3.1. Три кита ООП.** [S1, S5]
- **Инкапсуляция** — сокрытие внутреннего состояния за публичным API; **наследование** — дочерний класс перенимает поведение родителя; **полиморфизм** — под одним интерфейсом разные реализации.
- Полиморфизм на примере: пульт с кнопкой «включить», а реализация у разных телевизоров разная (S5).

**A3.2. Интерфейсы vs абстрактные классы.** [S4, S5]
- **Интерфейс** — контракт: только сигнатуры (public-методы, константы, с 8.4 — и свойства). **Абстрактный класс** — иерархия наследования с общей реализацией; экземпляр создать нельзя.
- Выбор: интерфейс — когда нужен контракт, а реализация подставляется через DI; абстрактный класс — когда есть общая логика.
- 💡 Ловушка LSP: «пингвин не летает» — если у абстрактной «Птицы» есть `fly()`, а пингвин не летает, полёт лучше вынести в интерфейс.

**A3.3. Трейты (traits).** [S5] 🪤
- Механизм переиспользования кода (композиция) в условиях одиночного наследования PHP.
- Плюсы: горизонтальное переиспользование без наследования; удобно для `final`-классов.
- Минусы: сложнее трассировать, конфликты имён (решаются `insteadof`/`as`), нельзя типизировать аргумент «по трейту».
- ⚠️ Кандидат назвал трейты «решением многопоточности» — неверно: это про переиспользование кода, не про потоки.

**A3.4. `final` у класса.** [S5] 🪤
- `final class` запрещает наследование; `final`-метод — переопределение.
- Минус: финальные классы нельзя нормально замокать (мокинг через наследование) — приходится лезть в рефлексию.
- ⚠️ `final` ставится у классов, методов и (с 8.1) констант, но **не у обычных свойств**.

**A3.5. `self` vs `static`.** [S4] 🪤
- Про **позднее статическое связывание** (late static binding).
- `self` — раннее связывание: вызов привязан к классу, где написан `self`.
- `static` — позднее: вернёт/вызовет класс, из которого реально вызван (дочерний) — решает проблему наследования. Появился в PHP 5.3.

**A3.6. Магические методы.** [S4, S5]
- Полный набор: `__construct`, `__destruct`, `__clone`, `__toString`, `__invoke`, `__serialize`/`__unserialize` (современная замена `__sleep`/`__wakeup`, 7.4+).
- `__destruct` в PHP обычно не нужен (в C++ обязателен); пригодится в воркерах/асинхронщине.

**A3.7. `__invoke`.** [S5]
- Позволяет вызывать объект как функцию (`$obj()`). В Laravel — invokable-контроллеры: фреймворк через рефлексию вызывает класс как обработчик роута без явного имени метода.

**A3.8. `clone`.** [S5, S4]
- По умолчанию — **поверхностная (shallow)** копия: объект копируется, вложенные объекты/ссылки — нет.
- Глубокую копию даёт переопределение `__clone` (создаём новые вложенные экземпляры) или `serialize`/`unserialize`.
- Осторожно с ресурсами (resource-дескрипторы) — клонирование ведёт себя специфично.

**A3.9. Атрибуты.** [S4]
- Появились в PHP 8.0, работают через Reflection API; заменили docblock-аннотации (phpdoc).
- Symfony строится на атрибутах (валидация entity); в Laravel — подписка слушателя на событие.
- 💡 Нативный способ добавлять метаданные, читаемые рефлексией.

**A3.10. SOLID: LSP и DIP в контексте PHP.** [S3, S4, S5]
- **L (Liskov)** — подстановка: наследник должен корректно заменять родителя. Нарушение из S3: у наследника `saveUser(name, email, role)` появился обязательный аргумент, которого нет у родителя `saveUser(name, email)` — код, работавший с родителем, сломается. Выход — дефолтное значение нового аргумента.
- **D (Dependency Inversion)** — зависимость от абстракций, а не от конкретики; решается **интерфейсами** + DI. ⚠️ Кандидат в S5 сначала назвал OCP/LSP — правильный акцент DIP.
- **S (Single responsibility)** — вынести `exportUsers`/`sendWelcomeEmail` из `UserManager` (S3).
- **O (Open/closed)** — захардкоженная зависимость, которую нельзя подменить (S3).
- **I (Interface segregation)** — экспортеры CSV/JSON объединить под интерфейс (S3).
- 💡 Зрелая позиция (ценится): не каждый принцип SOLID надо втыкать везде — иначе «Hello World в абстрактных фабриках» (S3).

## A4. Autoload, Composer, PSR

**A4.1. Автозагрузка: PSR-4, Composer, `spl_autoload_register`.** [S3, S4]
- PSR-0 — первый стандарт автозагрузки; **PSR-4** — действующий (PSR-0 устарел).
- Composer: в `composer.json` секция `autoload` маппит папку (`src` → namespace `App`); генерирует `vendor/autoload.php`, который `require`-ится в `index.php`.
- Самому реализовать можно через **`spl_autoload_register`** — регистрирует функцию автозагрузки; объявленная позже — переопределяет композеровскую.

**A4.2. Что делает `use` и как работает автозагрузка.** [S4, S3]
- `use` — **импорт/алиас** имени класса из namespace; сам по себе ничего не подгружает — подгрузку выполняет автозагрузчик.
- Composer строит карту «namespace ↔ путь» и подгружает класс по запросу, избавляя от ручных `include`/`require`.
- Бонус namespace'ов: два класса с одинаковым именем из разных namespace'ов + алиас `use ... as ...`.
- Если файл не найден: при `include` — warning, при `require` — fatal error (S3).

**A4.3. `composer install` vs `composer update`.** [S4, S5]
- `install` — ставит зависимости по зафиксированным версиям из `composer.lock`.
- `update` — обновляет до последних допустимых версий и **переписывает** `composer.lock`.
- ⚠️ `update` в проде опасен: зависимости могут обновиться и сломать оттестированное приложение.

**A4.4. `composer.lock` vs `composer.json`; коммитить ли lock.** [S4, S5] ⚠️
- `composer.json` — описание зависимостей и ограничений версий (`~`, `^`, `*`); `composer.lock` — генерируется Composer'ом, фиксирует **точные версии** (включая транзитивные) с хэшами.
- Lock **коммитится в репозиторий** — гарантирует воспроизводимую установку (кандидат в S4 сначала ошибся «нет»).
- ⚠️ Кандидат в S5 утверждал «Composer без lock не работает» — неверно: при удалении lock `install` разрешит зависимости заново по `composer.json` и создаст новый lock; риск в «уехавших» версиях, не в падении.

**A4.5. Есть ли `composer.lock` внутри пакетов.** [S5]
- У каждого пакета свой `composer.json`, но `composer.lock` в **библиотечных** пакетах не используется — lock имеет смысл только для корневого приложения. Полный граф фиксирует корневой `composer.lock`.

**A4.6. Приватные пакеты Composer.** [S5]
- Опыта у кандидата не было, принцип: пакет описывается в `composer.json`, публикуется, подключается как зависимость; общий пакет можно шарить между микросервисами.

**A4.7. PSR — что это и основные стандарты.** [S5]
- PSR = PHP Standards Recommendation; выпускает **PHP-FIG** (Framework Interop Group).
- Основные: PSR-1 (базовый кодстайл), **PSR-4** (автозагрузка), PSR-12 (расширенный code style), PSR-6/PSR-16 (кэш), PSR-7 (HTTP-сообщения), PSR-18 (HTTP-клиент).
- ⚠️ Кандидат не назвал точные номера — интервьюер подтвердил: цифры не критичны, важно назначение.

## A5. PDO и доступ к БД

**A5.1. Подключение к MySQL: PDO vs MySQLi.** [S1]
- Оба расширения; PDO предпочтительнее: поддерживает **несколько БД**, prepared statements, лучшая безопасность.
- Указываешь сервер, юзер, пароль, имя БД; обрабатывай ошибки соединения, закрывай неиспользуемые соединения.

**A5.2. Prepared statements и SQL-инъекция.** [S1, S3] 🔧
- Prepared statement **отделяет SQL от пользовательского ввода** — инъекция вида `1; DROP DATABASE users` не сработает.
```php
$stmt = $pdo->prepare("SELECT * FROM users WHERE email = :email");
$stmt->execute(['email' => $email]);
```
- Главный фикс от инъекций — именно prepared statement; валидация типа (например, что это `int`) — лишь дополнение (S3).
- 💡 Признак профессионального стиля; заодно ускоряет повторяющиеся запросы.

**A5.3. `json_encode` и «тихий» null.** [S2, S3] ⚠️
- При ошибке `json_encode` **возвращает `null`/`false`** (не бросает exception) — и этот null «успешно распечатается» в результат.
- Лечение: передавать флаг **`JSON_THROW_ON_ERROR`** (бросает exception) или проверять `json_last_error()` / `JSON_ERROR_*`.
- Дополнительно: на больших данных — риск по памяти.

**A5.4. Маппинг результата на класс.** [S3]
- Вместо массива — `PDO::FETCH_*`, например `PDO::FETCH_CLASS`: мапит строку на объект/DTO, улучшает типизацию.

## A6. Ошибки и исключения

**A6.1. Как обрабатывать ошибки в PHP.** [S1]
- Валидация данных, `try-catch`, осмысленное логирование, понятные сообщения; **никогда не показывать пользователю чувствительную системную информацию**; искать корневую причину.

**A6.2. `try/catch` и `PDOException`.** [S3]
- При падении запроса PDO бросает **`PDOException`** (кандидат сказал «PDO result exception» — оговорка).
- ⚠️ Кандидат не помнил, поддерживает ли `PDO::query` множественные statements; суть — не интерполировать ввод, использовать prepared statements.

**A6.3. Семантика `get` vs `find`.** [S3]
- Договорённость: **`find`** возвращает null или результат, **`get`** — результат или **бросает exception**. Проверяй результат `fetch`: пусто → `UserNotFoundException`.

## A7. Безопасность PHP

**A7.1. `unserialize` и object injection.** [S3] 🪤
- `unserialize` задействует магические методы (`__wakeup`, `__unserialize`) — десериализация **недоверенных данных** может привести к object injection.
- Защита: передавать **`allowed_classes`** — список разрешённых классов, из строки сформируется только класс из перечисленных.

**A7.2. Как защищать PHP-приложение (общий чек-лист).** [S1]
- Валидация ввода, санитизация данных, prepared statements, хэширование паролей, HTTPS, безопасные сессии.
- Предотвращение **XSS** и **CSRF**; регулярное обновление зависимостей; ограничение прав на файлы.
- 💡 Безопасность — сквозная тема на всех этапах: разработка, тестирование, деплой, поддержка.

## A8. Сессии и cookies

**A8.1. Сессии vs cookies.** [S1]
- **Сессии** хранят данные пользователя **на сервере**; **cookies** — небольшие данные **в браузере**.
- Сессии безопаснее для аутентификации и чувствительных данных; cookies — для предпочтений/данных входа.
- (Флаги cookies — `HttpOnly`/`Secure`/`SameSite` — см. E1.2.)

# Часть B. Laravel и фреймворки PHP

**B1. Жизненный цикл запроса в Laravel.** [S5] 🔧
- Запрос → nginx → PHP-FPM → `public/index.php` (подключается автозагрузка Composer, создаётся приложение из `bootstrap/app.php`).
- Ядро (Kernel) определяет тип запроса (HTTP/Console); регистрируются service providers.
- Далее: **global middleware → роутинг → route middleware → контроллер → ответ**.
- ⚠️ Кандидат сначала поставил middleware до роутинга и смешал порядок; потом поправился: сначала определяется роут, затем отрабатывают middleware.

**B2. Middleware: в какие моменты вызывается.** [S5] ⚠️
- **Global** — до роутинга, для всех запросов. **Route** — после определения маршрута. **Terminable** — после отправки ответа (пост-обработка).
- ⚠️ Middleware ≠ валидация: «подготовить данные и выкинуть с хедером до роута» — это превалидация, а не middleware.

**B3. Фасады Laravel.** [S5]
- Фасад — синтаксический сахар: статический прокси к сервис-контейнеру; под капотом DI/контейнер инициализирует конкретный класс.
- Плюсы: краткий читаемый API. Минусы: статика, скрытые зависимости, сложнее тестировать; в **long-running** (RoadRunner/Swoole/Octane) статический контекст может давать **утечки памяти**.
- 💡 Команда кандидата тоже предпочитает DI через конструктор.

**B4. Анемичная vs богатая модель.** [S5] 🧭
- **Анемичная** — «пустая»: свойства и связи, логика в репозиториях/сервисах. **Богатая (rich)** — данные + логика поведения.
- Active Record (Eloquent) часто ведёт к анемичной модели и нарушению SRP; Data Mapper (Doctrine) — ближе к разделению контекста.

**B5. Сервис-контейнер / DI / рефлексия.** [S5]
- Контейнер работает на **рефлексии**: анализирует сигнатуру конструктора и автоматически (autowiring) разрешает зависимости + кэширует резолв.
- Сервис-провайдеры регистрируют биндинги (singleton vs transient).
- Два способа достать экземпляр: **DI** (автоматически) или **сервис-локатор** (`app()->make()`). Сервис-локатор — хардкод зависимостей, хуже контролируется; лучше чистый DI.
- **Reflection API** — интроспекция классов/методов/свойств в рантайме; на ней строится autowiring и invokable-контроллеры.

**B6. Swoole / RoadRunner / FrankenPHP; Laravel vs Symfony.** [S5]
- Laravel тратит больше времени на инициализацию ядра (тянет сервис-провайдеры), чем Symfony; Symfony агрессивнее кэширует роутинг и DI в PHP-файлы.
- Long-running/асинхронные серверы — **Swoole, RoadRunner, FrankenPHP** — держат инициализированное приложение в памяти и отдают доступ быстро.
- Swoole — ради многопоточности/корутин (асинхронные рутины, мьютексы, семафоры), фактически «заместитель PHP-FPM». RoadRunner (Go) держит ядро поднятым, но в плане многопоточности ближе к FPM (worker-процессы).

**B7. Очереди, джобы, события/слушатели.** [S5]
- Jobs (через `dispatch`) — тяжёлые/фоновые вычисления; events/listeners — на одно событие несколько слушателей (гибче), job — одиночная единица работы.
- Воркеры (`php artisan queue:work`) тащат задачи из очереди (Redis) асинхронно; поднимаются через Supervisor.
- Listener по умолчанию выполняется **синхронно** в том же процессе, что и диспатч; в фон уходит, только если реализует `ShouldQueue`.

**B8. Supervisor — зачем и аналоги.** [S5] 🧭
- Демон, держит worker-процессы живыми (воркеры умирают — перезапуск).
- Аналоги: Docker (restart-политики), systemd, репликация подов в Kubernetes.

**B9. Авторизация: Sanctum / Passport / JWT.** [S5]
- **Sanctum** — token-based (SPA-токены, personal access tokens); **Passport** — полноценный OAuth2-сервер; JWT-библиотеки (`tymon/jwt-auth`).

**B10. Почему парсить JWT на PHP на хайлоуде плохо.** [S5] 💡
- Разбор/верификация подписи JWT на каждый запрос грузит CPU → на высоком RPS узкое место.
- Варианты: вынести проверку на **nginx (Lua/OpenResty)** — быстрее PHP; отдельный auth-микросервис для простой проверки токена — **переусложнение** (интервьюер заметил).
- 💡 Сначала думать о месте валидации (edge), не городить микросервисы.

**B11. Дебаггинг.** [S5]
- Tinker, консольные команды, Postman, Xdebug, `dd()/dump()`, `laravel-debugbar` (смотреть формируемые запросы, ловить N+1).

**B12. MVC и фреймворки (общее).** [S1, S5]
- MVC = Model (данные) — View (интерфейс) — Controller (обрабатывает запрос, координирует).
- Фреймворки (Laravel, Symfony, CodeIgniter, CakePHP) упрощают роутинг, аутентификацию, работу с БД, валидацию.
- 💡 Называй фреймворки, с которыми реально работал, и подчёркивай следование конвенциям.

# Часть C. 🧭 Не-PHP: SQL и базы данных

## C1. SQL: базовые конструкции

**C1.1. WHERE vs HAVING.** [S3, S5, S4]
- `WHERE` фильтрует **строки до группировки**; `HAVING` — **после GROUP BY**, по агрегатам (`COUNT`, `SUM`).
- 💡 Формулировка-памятка: «WHERE — по строкам, HAVING — по группам».

**C1.2. HAVING без GROUP BY.** [S3] ⚠️
- `HAVING` без группировки допустим — весь результат трактуется как одна группа; типичное место — после GROUP BY.
- ⚠️ Кандидат ответил «ругается» (ошибка `must appear in GROUP BY or be used in an aggregate function` относится к колонкам в SELECT, а не к самому HAVING); интервьюер принял формулировку про агрегатный контекст.

**C1.3. Виды JOIN.** [S3] 🪤
- **INNER** — только совпавшие строки. **LEFT/RIGHT** — все строки одной стороны, у другой NULL. **FULL OUTER** — все строки обеих. **CROSS** — **декартово произведение** (каждая × каждая), а не «пересечение» (кандидат путал).
- Пользователи без корзин: INNER их не выведет; LEFT JOIN → NULL у корзины.

**C1.4. CROSS JOIN — зачем.** [S3]
- Генерация всех комбинаций строк двух таблиц. ⚠️ Кандидат не смог назвать применение.

## C2. Индексы

**C2.1. Что такое индекс, типы, плюсы/минусы.** [S4, S5]
- Структура, ускоряющая `SELECT`; хранится на диске; **замедляет INSERT/UPDATE/DELETE** (пересчёт/перебалансировка).
- B-tree (сбалансированное дерево; листья связаны как список — ускоряет диапазонные выборки). Без индекса — full scan.
- Типы: primary key, unique, обычный B-tree, составной (composite), hash, полнотекстовый, частичный (partial), GIN/GiST (Postgres: JSONB, геоданные, полнотекст).

**C2.2. Селективность; индекс на bool.** [S4, S2, S3] 🪤
- Ключевое понятие — **селективность**. На низкоселективные поля (bool 50/50, gender, `status` с двумя значениями) индекс почти бесполезен: «срежем в половину» — перебор всё равно большой.
- Имеет смысл при высокой селективности (true у ~10% — поможет; true у 90%+ — оптимизатор выберет full scan).
- В составном индексе **слева — самое селективное поле**.
- 💡 Термин «селективность» надо уметь назвать (кандидаты в S2/S3/S4 спотыкались).

**C2.3. Когда индексы вредят.** [S2, S4]
- Не используется — место без пользы; замедляет INSERT/UPDATE/DELETE; маленькие таблицы — seq scan часто быстрее; низкая селективность — бесполезен.
- На большой таблице — `CREATE INDEX CONCURRENTLY` (без блокировки записи). ⚠️ Создание индекса на живой таблице может её заблокировать (S3).

**C2.4. Покрывающий индекс (covering).** [S3]
- Синтаксис `INCLUDE (...)` — поля не индексируются, но кладутся в лист индекса: найдя значение, не ходить в таблицу (Index Only Scan).

**C2.5. Как проверить, что индексы работают.** [S3]
- **`EXPLAIN`** (можно `EXPLAIN ANALYZE`): видно `using index` и имя используемого индекса; алгоритмы и порядок джойнов.

## C3. Транзакции и изоляция

**C3.1. Что такое транзакция.** [S3]
- Несколько операций как одна, «всё или ничего» (атомарность, ACID); нужна для консистентности данных (списание у одного → начисление другому без промежуточного состояния).

**C3.2. Уровни изоляции.** [S3]
- `Read uncommitted`, `Read committed`, `Repeatable read`, `Serializable`; по умолчанию в PostgreSQL — **Read committed**.
- **Read committed**: видны только закоммиченные данные других транзакций.
- **Repeatable read**: снимок на момент начала транзакции; защищает от **неповторяющегося чтения**; фантомные чтения остаются.
- Аномалии: грязное чтение, неповторяющееся чтение, фантомное чтение, потерянное обновление.

## C4. Репликация и масштабирование

**C4.1. Репликация: зачем и как.** [S5, S4]
- Master-slave: пишем в мастер, читаем с реплик (запросов на чтение обычно больше). Горизонтальное масштабирование + отказоустойчивость.
- Синхронная/асинхронная; при асинхронной возможен **replication lag** → eventual consistency (нужна обработка неконсистентности).

**C4.2. Failover: могут ли мастер и реплика поменяться.** [S5] ⚠️
- Да — при падении мастера переключаемся на реплику (новый мастер), сервис продолжает работать.
- Риск: при асинхронной репликации часть данных могла не доехать → несогласованность.
- ⚠️ Кандидат ушёл в описание lag, а главный сценарий — отказоустойчивость при падении сервера БД.

**C4.3. Масштабирование БД.** [S4, S5]
- **Партиционирование** — встроенный механизм PostgreSQL: таблица делится на партиции, БД сама знает куда обращаться.
- **Шардирование** — данные по разным базам (финтех); ключ шардирования — по бизнес-логике доступа.
- «Много читаем, мало пишем» → репликация (чтение разгружает мастер).

## C5. Блокировки и миграции

**C5.1. Блокировки в БД.** [S5]
- Уровни: база, таблица, строка. На уровне строк: `FOR UPDATE` (эксклюзивная), `FOR NO KEY UPDATE`, `FOR SHARE` (менее эксклюзивная).

**C5.2. Тяжёлая миграция (смена типа колонки).** [S5] ⚠️ 🔧
- Наивный `ALTER ... TYPE` (integer → bigint) на миллионах строк берёт тяжёлую блокировку (в Postgres — `ACCESS EXCLUSIVE`) → простой.
- Безблокировочный путь:
  1. Новая колонка нужного типа **с NULL и без DEFAULT** (в Postgres — мгновенно, только метаданные).
  2. В коде — двойная запись в обе колонки.
  3. Фоном батчами перенос/конвертация старых данных.
  4. Переключить код, удалить старую колонку.
- Инструменты: online schema change, gh-ost / pt-online-schema-change (MySQL), pg-osc (Postgres).
- ⚠️ Кандидат долго искал (батчи, дамп, партиционирование — мимо); решение подсказал интервьюер.

## C6. CTE и JSON

**C6.1. CTE (`WITH`).** [S3]
- Формирует временную «вьюшку», живущую в памяти на время запроса; можно создавать сколько угодно и использовать в джойнах.
- Производительность: создание/хранение в памяти аффектит базу. Если подзапрос нужен дважды — лучше `WITH` (посчитали один раз); простой/маленький — можно и подзапрос.

**C6.2. JSON-поля.** [S2]
- Trade-off: реализация через JSON или отдельные таблицы. Через JSON — хуже по скорости и размеру базы; JSON можно индексировать, но «не очень шустро». Аргументация за нормализованные таблицы разумнее.

## C7. Нормализация и проектирование схем

**C7.1. Нормальные формы.** [S3]
- **1NF** — не пихать несколько значений в одно поле (разбить ФИО на три поля). **2NF** — избегать дублирования (вынести `resume_link`/`source`). **3NF** — ⚠️ кандидат не вспомнил.

**C7.2. Схема «компании и объявления».** [S2]
- Сущности: `users`, `companies`, `ads`, `countries`, `tags` + промежуточные таблицы для фильтров white/black list (многие-ко-многим): `country_rules`, `tag_rules` с флагом allow/forbid (boolean — третьего состояния нет).
- `status` — `varchar`, не `enum` (новый статус enum требует ALTER); `id` — UUIDv7 или unsigned bigint; soft delete через `deleted_at` (NULL не входит в unique-индекс → составной unique `name` + `deleted_at`).
- 💡 JSON в ТЗ — просто пример формата, к БД отношения не имеет.

**C7.3. Индексы для «компании/объявления».** [S2]
- По фильтруемым/джойнимым полям; на название стран — можно (таблица маленькая, индекс мал); на теги — да (поиск `LIKE` + `lower()`); на `deleted_at` — да (`WHERE deleted_at IS NULL`); на `status` — нет (низкая селективность); на `text` — нет (только полнотекст).

**C7.4. Схема рекрутинга (вакансии/кандидаты).** [S3]
- Таблицы: `departments`, `vacancies`, `vacancy_links`, `responses` (отклики), `interviews`, `notes`, `candidates`, `resume`, `source`.
- Ключевые решения: **развести «кандидата» и «резюме»** (один человек — несколько резюме под разные вакансии); в интервью ссылаться на `resume_id`; источник — отдельная таблица; динамические поля — **EAV** (`candidate_properties` + `property_values`).
- Индексы: внешние ключи + `status` (где статусов много) + `created`; не индексировать статус с двумя значениями.

**C7.5. Партнёрская программа (статистика).** [S2]
- `accounts` (наш id ↔ их id + токен), `statistics` (дата + метрики + `external_account_id` + geo). Хранить **конкретную дату** (не период) — иначе не агрегировать.
- Токен — **шифровать обратимо** (не хешировать: нужен исходник для вызова API).
- Закрытие месяца: два поля дат — `date` (бизнес-дата) и `source_date` (дата в источнике); после закрытия — изменения запрещены (контроль на уровне приложения + `CHECK`/триггер в БД как страховка); возвраты в закрытом месяце — отрицательным числом.
- Обновление — фоновый воркер/крон с очередью job'ов, а не по кнопке (иначе 30+ сек ожидания); не полагаться на вебхук (его скорее не дадут).

**C7.6. Загрузка 30 млн записей (налоговая база).** [S6]
- Практическая задача: описать дизайн решения (что использовать, как построить, почему), влияние оптимизаций на производительность и как профилировать.
- Оценивается подход к мышлению, а не заученный ответ. (См. также: порционная/потоковая обработка при ограничении памяти — аналог генераторов A1.7.)

# Часть D. 🧭 Не-PHP: архитектура, сети, инфраструктура

## D1. Архитектура

**D1.1. MVC / DDD / гексагон / CQRS.** [S3]
- Не противоречат друг другу: MVC — про View/Controller, модель — доменный слой. View = DTO в ответе, контроллер = HTTP-слой инфраструктуры, модель = домен.
- **CQRS** — разделение чтения/записи; мотивация — высокие нагрузки на чтение (query-сторона читает напрямую из базы, минуя ORM).
- 💡 «MVC + DDD + гексагональная не противоречат» — грамотная позиция.

**D1.2. Coupling vs Cohesion.** [S5] ⚠️
- **Coupling (сцепление)** — связи **между** модулями, должно быть меньше. **Cohesion (связность)** — связи **внутри** модуля, должна быть высокой (модуль отвечает за свой контекст).
- Антипример — god-объекты («сервисы-боги»).
- ⚠️ Кандидат путал термины между собой.

**D1.3. Слоистая архитектура.** [S5, S3]
- Слои по DDD: **domain** (бизнес-логика), **application** (use cases), **infrastructure** (БД, интеграции), **presentation** (API/контроллеры).
- Паттерны: луковая (onion), гексагональная (ядро — бизнес, вокруг адаптеры/порты).

**D1.4. DDD-агрегат.** [S5]
- Агрегат — единица консистентности: одна точка входа (корень агрегата), связанные объекты меняются только через неё.

**D1.5. Микросервисы: что решают и грабли.** [S5]
- Решают: вынос высоконагруженного модуля из монолита, независимый деплой, горизонтальное масштабирование, свой стек.
- Грабли выноса функции (отправка в ФНС): связанность → рефакторинг; выбор sync/async (брокеры) — async проще, но добавляет сложность; согласованность данных между базами; DevOps-нагрузка; разные стеки → узкие специалисты. «Можно всё, но вопрос — зачем».

**D1.6. Смена СУБД / внешних сервисов.** [S3]
- Смена СУБД — **суперредкий процесс**, гибкость под него часто не нужна. ORM умеют работать с разными БД, но платим производительностью.
- Внешние сервисы — через **интерфейс + инверсию**: реализации под единым интерфейсом, взаимозаменяемые через feature-флаги/env.
- Минимизация рисков: кэш read-запросов, fallback, понятная ошибка, версионирование API, стабы для тестов.

**D1.7. SOLID (общее).** [S4, S5] — полный разбор LSP/DIP и остальных принципов — в A3.10. Краткая шпаргалка: S — одна ответственность, O — открыт/закрыт, L — подстановка Лисков, I — разделение интерфейсов, D — инверсия зависимостей.

**D1.8. Паттерны проектирования.** [S4]
- Базовый набор: Singleton, Factory (Abstract/Factory Method/Simple), Decorator, Adapter, Proxy, Chain of Responsibility, Iterator, Strategy, Builder.
- Применение на практике: CQRS (разделение чтения/записи), **Decorator** (оборачивал репозиторий кэшем), **Builder** (DTO), **Singleton** (service provider), **Strategy** (драйверы платёжки).
- ⚠️ Кандидат путался Strategy / Abstract Factory / Factory Method: Strategy — выбор алгоритма через общий интерфейс; Factory — порождение объектов.

## D2. Сети и HTTP

**D2.1. TCP vs UDP.** [S4]
- TCP — гарантирует доставку (установка соединения, порядок, повторная отправка). UDP — «прямой поток» (VoIP/стриминг): пакеты могут теряться, зато быстрее.

**D2.2. Что происходит при вводе google.com.** [S4]
- DNS → IP; TCP-рукопожатие; nginx/apache принимает → статика или прокси в PHP-FPM → приложение (Laravel).
- ⚠️ Базовая схема без TLS/HTTPS, структуры HTTP-запроса/ответа, статус-кодов (интервьюер: «возможно»).

**D2.3. Таймауты.** [S4] 💡
- Защищают от «бесконечных» запросов и зависших соединений; nginx отдаёт 504 при превышении порога.
- Для PHP-FPM: пул воркеров ограничен — зависшие запросы исчерпывают пул (self-DoS) → приложение недоступно.
- Долгие операции (генерация документа) — выносить в фон/очереди.

## D3. Очереди и брокеры

**D3.1. Зачем очереди.** [S4, S5]
- Вынести долгие/некритичные операции (email, уведомления, логирование) в асинхронный фон; пользователь получает ответ «здесь и сейчас».

**D3.2. At least once / at most once / exactly once.** [S4] ⚠️
- Семантика доставки: at-least-once (возможны дубли), at-most-once (возможны потери), exactly-once (труднодостижимо, требует идемпотентности).
- ⚠️ Кандидат не знал терминологию.

**D3.3. Poison message и DLQ.** [S4]
- Сообщение падает → возвращается в очередь → снова падает: счётчик повторов + лимит (max attempts, например 3) → мёртвая очередь (**DLQ**).

**D3.4. Брокер упал — как не потерять сообщения.** [S3]
- В RabbitMQ — флаг **durable/persistent** при создании очереди: сообщения бэкапятся на диск, а не в памяти. В Symfony включено по умолчанию.
- Платёжная система с polling: ретраи с паузами + **dead letter queue** — «задержка оплат (плохо, но не критично) вместо потери (критично)».

## D4. Docker, K8s, Git, observability

**D4.1. Docker — зачем.** [S5]
- Консистентное окружение для dev/prod, быстрый запуск; контейнер — изолированный процесс на ресурсах хоста, легче VM (VM — полноценная ОС).

**D4.2. Kubernetes — что решает.** [S5]
- Оркестрация: self-healing, распределение нагрузки, rolling-обновления. Для отказоустойчивости — 3+ ноды.

**D4.3. Git merge vs rebase.** [S4]
- `merge` — обычное слияние, **сохраняет историю**. `rebase` — **переписывает историю** (можно потерять коммиты); допустим при одиночной работе в ветке, в команде — лучше merge.

**D4.4. Атомарная запись файла.** [S4] 🪤 🔧
- Исключить состояние «записали половину и упали»: `fwrite` сбрасывает по кусочкам → не годится.
- Правильно: писать во **временный файл рядом**, затем **`rename()`** — на уровне ОС атомарен (либо целиком, либо нет).
```php
file_put_contents($tmp = $path . '.tmp', $data);
rename($tmp, $path);
```

**D4.5. Профилирование PHP.** [✍️] 🧭
- **Xdebug** (локально/стенд): profiler → cachegrind-файлы → Qcachegrind/Webgrind — видно, где жрёт CPU. Для памяти Xdebug 3 профиля не даёт — Blackfire/APM-агенты или снятие `memory_get_peak_usage()` в ключевых точках.
- На проде Xdebug не вешают (сильно тормозит; плюс это инструмент разработчика — см. E1.1 «профайлеры на проде отключить»). Продакшен-инструменты — APM (Datadog/New Relic) или OTel.
- «Прод тормозит» в PHP чаще не CPU: исчерпан **FPM-пул** (зависшие запросы, таймауты), SQL без индекса (EXPLAIN), внешние вызовы — трейс показывает сразу.

**D4.6. Трейсинг в PHP-проекте.** [✍️] 🧭
- **OpenTelemetry PHP**: SDK + автоинструментация (интеграции Symfony/Laravel), экспорт по OTLP.
- Фоновые задачи: **traceparent в заголовках сообщения** при публикации в очередь (RabbitMQ/Symfony Messenger) — воркер продолжает трейс родителя, а не начинает новый.
- trace ID в логах: **Monolog-процессор** — корреляция лог ↔ трейс (см. [не-языковой банк](non-language-question-bank.md), D3.7).

**D4.7. Инструменты observability (быстрый ответ).** [✍️] 🧭
- Метрики — **Prometheus** (+ Grafana), логи — ELK/Loki, трейсы — Jaeger/Tempo, стандарт — **OpenTelemetry (OTLP)**.
- Канон с ответами — [не-языковой банк](non-language-question-bank.md), D3; здесь не дублирую.

# Часть E. 🧭 Не-PHP: безопасность, алгоритмы, поведенческие

## E1. Безопасность (общие уязвимости)

**E1.1. С какими уязвимостями сталкивался и защита.** [S3]
- SQL-инъекция (prepared statements — A5.2). Перебор уязвимых файлов (`phpinfo()`, конфиги): в публичном доступе — только `index.php`, профайлеры на проде отключить. **XSS** — чужой JS исполняется в браузере жертвы. XML/ZIP-бомбы. Открытые порты (сканер nuclei). Повышение привилегий. Отсутствие TLS (сниффинг).

**E1.2. Защита кук: флаги.** [S3] ⚠️
- **`HttpOnly`** — запрещает доступ из JS (`document.cookie`), защита от кражи через XSS. **`Secure`** — только по HTTPS. **`SameSite`**, **`Domain`**.
- ⚠️ Кандидат назвал только SameSite/Domain, пропустил HttpOnly и Secure.

**E1.3. Почему нельзя MD5 для паролей.** [S3] ⚠️
- Быстрые коллизии + **timing attack** (по времени ответа подбираем символ).
- Нужны современные алгоритмы с **солью**: bcrypt/argon2id. MD5 подбирается за час, современный — ~10 лет.

**E1.4. JWT: что это и зачем.** [S3]
- JSON Web Token — метод авторизации наравне с сессиями; нужен в **распределённых системах** (несколько серверов, сессии не шарить).
- Содержит информацию о пользователе (issuer, expiration); три части через точку (base64). Даёт отзыв токенов, разгрузку (проверка блокировки вместо существования).

## E2. Алгоритмы

**E2.1. Разворот массива (задача с багом).** [S5] 🪤 🔧
- Функция с багом: цикл по **всем N**, а не по **N/2** → массив разворачивается дважды и возвращается в исходный порядок.
```php
// Багнутая версия из источника: цикл по всем N → разворачивает дважды
function reverseArray(array $array): array
{
    $temp = 0;
    for ($i = 0; $i < count($array); $i++) {
        $temp = $array[$i];
        $array[$i] = $array[count($array) - $i - 1];
        $array[count($array) - $i - 1] = $temp;
    }
    return $array;
}
```
- Для `[1,2,3,4,5,6]` результат — снова `[1,2,3,4,5,6]`. Фикс: `$i < intdiv(count($array), 2)`.
- На практике — **`array_reverse()`**, не изобретать велосипед (встроенные функции оптимизированы).
- ⚠️ Кандидат ошибся в ручной трассировке индексов (считал «от единицы», а не от нуля).
