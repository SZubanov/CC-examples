# Часть A. SQL и базы данных

## A1. SQL-конструкции

**A1.1. WHERE vs HAVING.** [G2, G3, G4, P3, P4, P5]
- `WHERE` фильтрует **строки до группировки**; `HAVING` — **группы после GROUP BY**, по агрегатам (`COUNT`, `SUM`).
- 💡 Формулировка-памятка: «WHERE — по строкам, HAVING — по группам».

**A1.2. HAVING без GROUP BY.** [P3] ⚠️
- Допустим: весь результат трактуется как **одна группа**. ⚠️ Кандидат ответил «ругается» — ошибка `must appear in GROUP BY or be used in an aggregate` относится к колонкам в SELECT, а не к самому HAVING.

**A1.3. Виды JOIN.** [G3, P3] 🪤
- **INNER** — только совпавшие строки. **LEFT/RIGHT** — все строки одной стороны, у другой NULL. **FULL OUTER** — все строки обеих. **CROSS** — **декартово произведение**, а не «пересечение» (кандидаты путали).
- Пользователи без корзин: INNER их не выведет; LEFT JOIN → NULL у корзины.

**A1.4. CROSS JOIN — зачем.** [P3] ⚠️ — генерация всех комбинаций строк двух таблиц. ⚠️ Кандидат не смог назвать применение.

**A1.5. Топ-N: стандартный скелет (до автоматизма).** [G3, G6] 🔧
```sql
SELECT c.email, SUM(carts.amount) AS total
FROM customers c
JOIN carts ON carts.customer_id = c.id
WHERE c.country = 'Россия'          -- фильтр ДО группировки
GROUP BY c.id
HAVING SUM(carts.amount) >= 1000    -- фильтр ПОСЛЕ группировки
ORDER BY total DESC
LIMIT 10;
```
- Скелет: **JOIN → WHERE → GROUP BY → HAVING → ORDER BY DESC → LIMIT**.
- Агрегаты: SUM/MIN/MAX/COUNT; `string_agg(title, ', ')` — перечисление через разделитель (PostgreSQL).
- Всё, что в SELECT при GROUP BY, — либо группируемое, либо агрегат.

**A1.6. CTE (`WITH ...`).** [P3]
- Временная «вьюшка» в памяти на время запроса; можно создавать несколько и джойнить.
- Производительность: хранение в памяти аффектит базу. Подзапрос нужен дважды → `WITH` (посчитали раз); маленький/простой — подзапрос ок.

## A2. Индексы

**A2.1. Что такое индекс, типы, плюсы/минусы.** [P4, P5, G2]
- Структура, ускоряющая `SELECT`; хранится на диске; **замедляет INSERT/UPDATE/DELETE** (пересчёт). Без индекса — full scan.
- B-tree (сбалансированное; листья связаны списком — быстрые диапазонные выборки). Типы: primary key, unique, обычный, составной (composite), hash, полнотекстовый, частичный, GIN/GiST (Postgres: JSONB, гео, полнотекст).

**A2.2. Селективность; индекс на bool.** [G1, P2, P3, P4] 🪤
- Ключевое понятие — **селективность**. Низкоселективные поля (bool 50/50, gender, `status` с двумя значениями) → индекс почти бесполезен («срежем в половину» — перебор всё равно большой).
- Имеет смысл при высокой селективности (true у ~10% — поможет; у 90%+ — оптимизатор выберет full scan). В составном индексе **слева — самое селективное поле**.
- 💡 Термин «селективность» надо уметь назвать — кандидаты в G1/P2/P3/P4 спотыкались.

**A2.3. Когда индексы вредят.** [G2, G4, P3, P4]
- Не используется — место без пользы; замедляет INSERT/UPDATE/DELETE; маленькие таблицы — seq scan часто быстрее; низкая селективность — бесполезен.
- На большой таблице — **`CREATE INDEX CONCURRENTLY`** (без блокировки записи). ⚠️ Создание индекса на живой таблице может её заблокировать [P3].

**A2.4. Покрывающий индекс (covering).** [P3]
- `INCLUDE (...)` — поля не индексируются, но кладутся в лист индекса: найдя значение, не ходить в таблицу (Index Only Scan).

**A2.5. Как проверить, что индексы работают.** [G1, G3, P3]
- **`EXPLAIN`** (можно `EXPLAIN ANALYZE`): видно `using index` и имя индекса, алгоритмы и порядок джойнов. Если DBA «что-то с запросом» — начинай с EXPLAIN.

**A2.6. Vacuum (PostgreSQL).** [G1] — очистка мёртвых версий строк (MVCC). Достаточно общего понимания.

## A3. Транзакции и изоляция

**A3.1. Что такое транзакция, ACID.** [P3]
- Несколько операций как одна, «всё или ничего» (атомарность). ACID = Atomicity, Consistency, Isolation, Durability. Нужна для консистентности (списание у одного → начисление другому без промежуточного состояния).

**A3.2. Уровни изоляции.** [G1, G3, P3]
- `Read uncommitted` → `Read committed` → `Repeatable read` → `Serializable`. По умолчанию в PostgreSQL — **Read committed**.
- **RC**: видны только закоммиченные данные. **RR**: снимок на момент начала транзакции, защищает от неповторяющегося чтения; **фантомы остаются**. ⚠️ Поправка: в PostgreSQL READ UNCOMMITTED трактуется как READ COMMITTED (не поддерживается отдельно).
- Аномалии: грязное чтение, неповторяющееся чтение, фантомное чтение, потерянное обновление (lost update).

**A3.3. Списание баланса: задача с подвохом.** [G3] 🪤 🔧
- Проблема №1: **float для денег — ошибка**, только целые минимальные единицы (2350 ₽ = 235000).
- Проблема №2: read committed + два параллельных списания → **lost update** (обе прочитали баланс, каждая записала своё). Это НЕ «грязное чтение» (RC его исключает) — кандидат ошибся в термине.
- Решения:
  - `SELECT ... FOR UPDATE` (блокировка до **конца транзакции**; при переводе между кошельками — блокировать обе строки **в фиксированном порядке** против дедлоков).
  - Атомарный UPDATE с условием: `UPDATE wallets SET balance = balance - 100 WHERE user_id = 42 AND balance >= 100;`
  - `CHECK (balance >= 0)` + безусловный UPDATE.
- Глобально повышать изоляцию не стоит («всё чётко, но просядет производительность»): точечная блокировка предпочтительнее.
- **Дедлок**: две транзакции держат строки друг друга; избегать порядком блокировок.

## A4. Репликация и масштабирование

**A4.1. Репликация master-slave.** [G3, G4, P4, P5]
- Пишем в мастер, читаем с реплик (чтений обычно больше). Горизонтальное масштабирование + отказоустойчивость.
- Синхронная/асинхронная; при асинхронной возможен **replication lag** → eventual consistency (нужна обработка неконсистентности).

**A4.2. Failover: смена мастера.** [P5] ⚠️
- Да: при падении мастера реплика становится новым мастером. Риск: при асинхронной репликации часть данных могла не доехать. ⚠️ Кандидат ушёл в описание lag, а главный сценарий — отказоустойчивость при падении сервера БД.

**A4.3. Вертикальное vs горизонтальное.** [G2] 🪤
- **Вертикальное** — наращивание ресурсов одной машины (CPU/память/диск) — есть **потолок**. ⚠️ Кандидат назвал вертикальным «деление по таблицам» — неверно.
- **Горизонтальное**: репликация (копии), шардинг (делим данные по строкам/таблицам), партиционирование (таблица делится внутри одной БД).

**A4.4. Шардинг: выбор ключа.** [G3]
- **По бизнес-логике доступа**: чаты → по чату, заказы → по региону/локации. Партиционирование проще всего **по времени** (created_at).

**A4.5. View vs материализованное представление.** [G4]
- **View** — алиас запроса, места не занимает; минус: перенос логики на сторону БД (часто антипаттерн).
- **Materialized view** — **кэшированный снимок**; обновляется `REFRESH MATERIALIZED VIEW`; историю не хранит.

## A5. Блокировки и миграции

**A5.1. Блокировки в БД.** [P5, G3]
- Уровни: база, таблица, строка. На уровне строк: `FOR UPDATE` (эксклюзивная), `FOR NO KEY UPDATE`, `FOR SHARE` (менее эксклюзивная).

**A5.2. Тяжёлая миграция (смена типа колонки).** [P5] ⚠️ 🔧
- Наивный `ALTER ... TYPE` (integer → bigint) на миллионах строк берёт тяжёлую блокировку (в Postgres — `ACCESS EXCLUSIVE`) → простой.
- Безблокировочный путь:
  1. Новая колонка нужного типа **с NULL и без DEFAULT** (в Postgres — мгновенно, только метаданные).
  2. В коде — двойная запись в обе колонки.
  3. Фоном батчами перенос/конвертация старых данных.
  4. Переключить код, удалить старую колонку.
- Инструменты: gh-ost / pt-online-schema-change (MySQL), pg-osc (Postgres). ⚠️ Кандидат долго искал (батчи, дамп — мимо), решение подсказал интервьюер.

## A6. Нормализация и проектирование схем

**A6.1. Нормальные формы.** [P3]
- **1NF** — не пихать несколько значений в одно поле (разбить ФИО). **2NF** — избегать дублирования (вынести `resume_link`/`source`). **3NF** — ⚠️ кандидат не вспомнил.

**A6.2. Схема «компании и объявления».** [P2]
- Сущности: `users`, `companies`, `ads`, `countries`, `tags` + промежуточные таблицы для фильтров white/black list (многие-ко-многим): `country_rules`, `tag_rules` с флагом allow/forbid.
- `status` — `varchar`, не `enum` (новый статус enum требует ALTER); `id` — UUIDv7 или unsigned bigint; soft delete через `deleted_at` (составной unique `name` + `deleted_at`).

**A6.3. Схема рекрутинга (EAV).** [P3]
- Развести **«кандидата» и «резюме»** (один человек — несколько резюме под разные вакансии); в интервью ссылаться на `resume_id`; источник — отдельная таблица; динамические поля — **EAV** (`candidate_properties` + `property_values`).
- Индексы: внешние ключи + `status` (где статусов много) + `created`; не индексировать статус с двумя значениями.

**A6.4. Партнёрская программа (закрытие месяца).** [P2]
- Хранить **конкретную дату** (не период) — иначе не агрегировать. Токен — **шифровать обратимо** (не хешировать: нужен исходник для вызова API).
- Закрытие месяца: два поля дат — `date` (бизнес) и `source_date` (в источнике); после закрытия изменения запрещены (контроль в приложении + `CHECK`/триггер); возвраты — отрицательным числом.
- Обновление — фоновый воркер/крон, не по кнопке; не полагаться на вебхук (его скорее не дадут).

**A6.5. Загрузка 30 млн записей (налоговая база).** [P6]
- Описать дизайн решения (что использовать, как построить, почему), влияние оптимизаций и как профилировать. Оценивается **подход к мышлению**, не заученный ответ. См. также порционную/потоковую обработку при ограничении памяти.

**A6.6. Схема библиотеки (многие-ко-многим).** [G6] 🪤
- Ловушка «Банда четырёх»: книга с 4 авторами не влезает в «author_id в books». Многие-ко-многим → связывающая таблица `book_authors`.
- Читатель↔книга: `reader_id` в books **nullable** + unique-constraint на `book_id` (максимум один читатель).

## A7. Диагностика производительности

**A7.1. «Тормозит сервис» — системный ответ.** [G5]
1. Логи → найти запрос (ID) → **trace ID** → весь путь.
2. **Дельта между логами** → место наибольшей задержки.
3. Какие запросы в этом куске → **EXPLAIN** (rows/cost, индексы, джойны).
4. Если код — **pprof** (Go) / Xdebug (PHP); поднять локально и прогнать.
- Отвечай из допущения, что в компании всё есть (Kibana, трейсинг). Не плоди технологии: сначала исчерпай БД (индексы, материализованные представления), Redis — крайний случай.

**A7.2. JSON-поля в БД.** [P2]
- Trade-off: JSON или отдельные таблицы. JSON — хуже по скорости и размеру; индексировать можно, но «не очень шустро». Аргументация за нормализованные таблицы разумнее.

# Часть B. Архитектура и системный дизайн

## B1. Архитектурные стили

**B1.1. MVC / DDD / гексагон / CQRS.** [P3]
- Не противоречат друг другу: MVC — про View/Controller, модель — доменный слой. View = DTO в ответе, контроллер = HTTP-слой, модель = домен.
- **CQRS** — разделение чтения/записи; мотивация — высокие нагрузки на чтение (query-сторона читает напрямую из базы, минуя ORM).
- 💡 «MVC + DDD + гексагональная не противоречат» — грамотная позиция.

**B1.2. Слоистая архитектура.** [P3, P5]
- Слои по DDD: **domain** (бизнес-логика), **application** (use cases), **infrastructure** (БД, интеграции), **presentation** (API/контроллеры).
- Паттерны: луковая (onion), гексагональная (ядро — бизнес, вокруг адаптеры/порты).

**B1.3. DDD-агрегат.** [P5]
- Единица консистентности: одна точка входа (корень агрегата), связанные объекты меняются только через неё.
- Детально — B5.5 (граница транзакции, ссылки по ID, одна транзакция = один агрегат).

## B2. Модульность

**B2.1. Coupling vs Cohesion.** [P5] ⚠️
- **Coupling (сцепление)** — связи **между** модулями, должно быть меньше. **Cohesion (связность)** — связи **внутри** модуля, должна быть высокой (модуль отвечает за свой контекст).
- Антипример — god-объекты («сервисы-боги»). ⚠️ Кандидат путал термины между собой.

**B2.2. Смена СУБД / внешних сервисов.** [P3]
- Смена СУБД — **суперредкий процесс**, гибкость под него часто не нужна. ORM умеют работать с разными БД, но платим производительностью.
- Внешние сервисы — через **интерфейс + инверсию**: реализации под единым интерфейсом, взаимозаменяемые через feature-флаги/env.
- Минимизация рисков: кэш read-запросов, fallback, понятная ошибка, версионирование API, стабы для тестов.

## B3. Микросервисы

**B3.1. Что решают и грабли выноса функции.** [P5, G4]
- Решают: вынос высоконагруженного модуля, независимый деплой, горизонтальное масштабирование, свой стек.
- Грабли выноса функции: связанность → рефакторинг; выбор sync/async (брокеры) — async проще, но добавляет сложность; согласованность данных между базами; DevOps-нагрузка; разные стеки → узкие специалисты. «Можно всё, но вопрос — зачем».

**B3.2. Минусы микросервисов.** [G4]
- Сложнее **отлаживать** (запрос по нескольким сервисам; сложнее откатывать; транзакционность между сервисами).
- Децентрализация: **не знаешь, что в других сервисах** (отдельные базы, отдельные команды).
- Взаимодействие медленнее (overhead данных) vs межпоточное в монолите; скорость разработки ниже для MVP; больше костов и поддержки.

## B4. SOLID и паттерны

**B4.1. SOLID (шпаргалка).** [P4, P5]
- S — одна ответственность · O — открыт/закрыт · L — подстановка Лисков (наследник корректно заменяет родителя) · I — разделение интерфейсов · D — инверсия зависимостей (зависимость от абстракций; решается интерфейсами + DI).
- 💡 Зрелая позиция: не каждый принцип надо втыкать везде — иначе «Hello World в абстрактных фабриках» [P3].

**B4.2. Паттерны проектирования.** [P4] ⚠️
- Базовый набор: Singleton, Factory (Abstract/Factory Method/Simple), Decorator, Adapter, Proxy, Chain of Responsibility, Iterator, Strategy, Builder.
- Применение: **Decorator** (обернуть репозиторий кэшем), **Builder** (DTO), **Singleton** (service provider), **Strategy** (драйверы платёжки), CQRS (разделение чтения/записи).
- ⚠️ Кандидат путал Strategy / Abstract Factory / Factory Method: Strategy — выбор алгоритма через общий интерфейс; Factory — порождение объектов.

## B5. DDD (прикладное): контексты, агрегаты, доменные события

> Добавлено под требование вакансии («Applied DDD practices: bounded contexts, aggregates, domain events») — блок под собеседование. В реальных выгрузках этих вопросов не было, поэтому все пункты авторские [✍️].
> Связанное: `reference/sources/design_event_sourcing_processing.md` (aggregate, hydration, projections), `design_payment_system.md` (outbox, saga, идемпотентность), `reference/wiki/cqrs.md`.

**B5.1. Что такое DDD и два его уровня.** [✍️]
- DDD (Eric Evans, «Domain-Driven Design») — подход к проектированию **сложной предметной области**: модель домена в центре, код говорит на языке бизнеса. Это не фреймворк и не набор паттернов.
- **Стратегический уровень**: язык, границы контекстов, карта контекстов, поддомены. Отвечает на «где какие модели и как они стыкуются».
- **Тактический уровень**: entity, value object, **aggregate**, **domain event**, repository, domain service. Отвечает на «как модель выглядит в коде».
- Поддомены: **core** — конкурентное преимущество (максимум внимания), **supporting** — нужен, но не уникален, **generic** — берём готовое, не пишем сами.
- 💡 Зрелый ответ: «в DDD главное — язык и границы, тактические паттерны вторичны». Ответ «агрегаты и репозитории» — уровень курса, а не senior.

**B5.2. Ubiquitous language (единый язык).** [✍️]
- Один словарь у команды и бизнеса: те же слова в разговоре и в коде (`Payment`, `Capture`, `Settlement`).
- Механизм: если бизнес говорит «платёж завис», а в коде `status = 5`, каждое обсуждение требует перевода — смысл теряется, ошибки в требованиях не видны.
- Зачем: падает стоимость коммуникации; термин, который нельзя произнести вслух, обычно означает, что понятия в домене нет — или в одну модель склеили два разных домена.
- Подвох: язык действует **внутри своего контекста** — вне его те же слова значат другое (см. B5.3).

**B5.3. Bounded context.** [✍️]
- Граница, внутри которой модель и язык **непротиворечивы**: одно слово — одно значение.
- Одно слово — разные модели: «Payment» в процессинге (статусы, ретраи к PSP, UNKNOWN) и «Payment» в леджере (проводки) — разные понятия; «Customer» в продажах, поддержке и биллинге тоже. Попытка сделать одну общую модель «на всю компанию» — источник конфликтов.
- **Контекст ≠ модуль ≠ сервис**: контекст — про модель и язык, модуль — про структуру кода, сервис — про деплой и масштаб. Один контекст спокойно живёт монолитом; вынос в сервис — следствие проведённой границы, а не цель DDD.
- 🪤 «DDD — это про микросервисы» — нет: границу контекста выбирают по домену.

**B5.4. Context map: как контексты соединяются.** [✍️]
- Карта контекстов: какие контексты есть и кто на кого влияет (upstream/downstream).
- Паттерны связей: **Shared Kernel** (общая часть модели), **Customer/Supplier** (заказчик–поставщик), **Conformist** (подстраиваемся под чужую модель), **Anticorruption Layer (ACL)** (переводчик на границе: чужая модель не протекает внутрь), **Open Host Service / Published Language** (публичный контракт), **Separate Ways**.
- Прикладное: ACL на границе с легаси и внешними API (PSP, банк) — их статусы и коды ошибок мапятся в наши на границе, а не разъезжаются по коду.
- ⚠️ Shared Kernel любят как «общий модуль на всех» — он связывает релизы команд: экономит на старте, дорого стоит потом.

**B5.5. Агрегат и корень агрегата.** [✍️]
- **Aggregate** — кластер объектов, который меняется как единое целое: это **граница консистентности и транзакции**, внутри которой инварианты выполняются всегда.
- **Aggregate root** — единственная точка входа: снаружи ссылаются только на корень и только по **ID**, состояние меняют только методами корня, внутренние объекты наружу не отдают.
- Правило транзакции: **одна транзакция — один агрегат**; между агрегатами — ссылка по ID и eventual consistency (событиями, см. B5.8).
- Агрегаты держат **маленькими**: чем крупнее, тем выше конкуренция за блокировку (lost update, дедлоки) и тем длиннее транзакция.
- Пример: `Payment` — агрегат с инвариантом «нельзя захватить отменённый платёж»; проводки в леджере — отдельный агрегат и контекст, синхронизация событиями.
- 💡 Признак неверной границы: хочется в одной транзакции править два объекта → похоже, это один агрегат; а если агрегат раздулся и любые правки конфликтуют — границу провели слишком широко.

**B5.6. Domain events (доменные события).** [✍️]
- Событие домена — факт, важный для бизнеса, в **прошедшем времени**: `PaymentCaptured`, `RefundIssued`, `PayoutRequested`. Неизменяемо; несёт aggregate id, версию агрегата, время, idempotency key, actor.
- Публикует **корень агрегата** в момент изменения состояния; подписчики — проекции, другие контексты, саги, уведомления, аудит.
- Зачем: развязывает агрегаты и контексты (не тащить чужие зависимости в транзакцию), даёт явный аудит «что произошло», заменяет часть кросс-агрегатных транзакций.
- **Domain event ≠ integration event**: домен-событие — внутреннее (in-process), его можно рефакторить; интеграционное — публичный контракт наружу (брокер/шина, версионирование, беднее по деталям). Перевод — на границе контекста.

**B5.7. Надёжная публикация события: transactional outbox.** [✍️]
- Проблема: состояние в БД и событие в брокере — две системы; распределённую транзакцию не берём.
- Решение: событие пишется в таблицу **outbox** в одной транзакции с состоянием; отдельный воркер (или CDC/Debezium) публикует и помечает отправленные.
- Доставка **at-least-once** → потребитель **идемпотентен** (idempotency key + дедупликация), см. `design_payment_system.md`.
- Альтернатива: event sourcing — событие само источник истины (для агрегатов, где нужна история: платёж, кошелёк; справочники — нет).
- 🪤 «Публикуем сразу после commit из хендлера» — падение между commit и publish теряет событие; публикация до commit — потребитель видит то, чего ещё нет.

**B5.8. Согласованность между агрегатами (сага).** [✍️]
- Внутри агрегата — строгая согласованность; **между агрегатами — eventual**: событие → реакция → компенсация.
- Длинный процесс (списание → capture у PSP → проводки → выплата) — **saga / process manager**: шаги + компенсации при сбое (refund/void), состояние процесса хранится отдельно.
- В монолите иногда позволяют себе транзакцию на два агрегата — это осознанный trade-off: правило «одна транзакция — один агрегат» про то, чтобы код выжил при выносе в отдельный сервис.
- 💡 Назвать вслух: «consistency — строгая внутри агрегата, eventual между» — ровно это проверяет интервьюер.

**B5.9. Когда DDD не нужен.** [✍️]
- CRUD-приложения и простые домены (админки, справочники, конфиги) → DDD = оверинжиниринг: абстракции дороже сэкономленного.
- **DDD-lite** (Fowler): берём стратегическую часть — язык, границы, контексты; тактические паттерны — по необходимости.
- Микросервисы ≠ DDD; «распределённый монолит» — симптом границ, нарезанных по техническим слоям, а не по домену.
- CQRS/event sourcing — не обязательная часть DDD: точечно там, где нужен аудит и история.
- 💡 Зрелая позиция: «DDD оправдан в сложном домене — платёжка, леджер; в админке я бы взял DDD-lite и не плодил абстракции».

**B5.10. «Как ты применял DDD?» — каркас ответа.** [✍️]
- Скелет: домен → где провели границу контекста → что сделали агрегатом и какой инвариант он защищал → какие события пошли наружу и как доставлялись → что это дало (метрика/эффект).
- Термины для EN-версии: bounded context, aggregate root, domain event, integration event, eventual consistency, transactional outbox, anti-corruption layer, ubiquitous language.
- `[нужно заполнить]` факты (проект, границы, инвариант, события, эффект) — берём из своего опыта; не выдумываем.

# Часть C. Сети, HTTP, брокеры

## C1. Сети

**C1.1. TCP vs UDP.** [G2, P4]
- TCP — гарантирует доставку (установка соединения, порядок, повторная отправка). UDP — «прямой поток» (VoIP/стриминг/игры): пакеты могут теряться, зато быстрее.

**C1.2. Что происходит при вводе google.com.** [P4] ⚠️
- DNS → IP; TCP-рукопожатие; nginx/apache принимает → статика или прокси в бэкенд (PHP-FPM/Go) → приложение.
- ⚠️ Базовая схема без TLS/HTTPS, структуры HTTP-запроса/ответа, статус-кодов (интервьюер: «возможно»).

**C1.3. Таймауты.** [P4] 💡
- Защищают от «бесконечных» запросов и зависших соединений; nginx отдаёт 504 при превышении порога.
- Для PHP-FPM: пул воркеров ограничен — зависшие запросы исчерпывают пул (self-DoS). Долгие операции — в фон/очереди.

## C2. HTTP

**C2.1. Структура HTTP-запроса, коды.** [G6]
- Запрос: метод, путь, версия протокола; headers — метаданные (Host, Content-Type); body — данные. **Host** — на одном IP несколько сайтов, сервер понимает к какому ресурсу.
- Коды: 200, 201 (Created), 204 (No Content), 301/302 (редиректы), 404. Свой HTTP-метод — формально можно, плохая практика.

**C2.2. HTTP/1.1 vs HTTP/2.** [G6] ⚠️
- 1.1 — текстовый протокол; 2 — **бинарные фреймы**. ⚠️ Парсинг есть в обоих (интервьюер придрался) — выигрыш в том, что фреймы **знают точную длину** и читаются однозначно быстрее.

**C2.3. gRPC.** [G2]
- Поверх **HTTP/2**, данные — **бинарный формат**, контракт — `.proto`, клиенты генерируются под любой язык, строгая типизация, стриминг. Для общения сервисов **внутри контура**.
- Почему не везде: сложность перехода, не везде HTTP/2, неудобно тестировать. ⚠️ Не «быстрее из-за шифрования» — суть бинарный протокол + HTTP/2.

## C3. Очереди и брокеры

**C3.1. Зачем очереди.** [P4, P5]
- Вынести долгие/некритичные операции (email, уведомления, логирование) в асинхронный фон; пользователь получает ответ «здесь и сейчас».

**C3.2. Kafka: партиции и реплики.** [G1]
- **Партиция** — логическая последовательность сообщений: **порядок** + распараллеливание обработки. **Реплика** — копия партиции **на другом брокере**: устойчивость; при падении — перебалансировка.

**C3.3. Consumer groups.** [G4] — объединяют консьюмеров: внутри группы **одна партиция не читается двумя консьюмерами**.

**C3.4. Гарантии доставки.** [G1, P4] ⚠️
- **at-least-once** (возможны дубли), **at-most-once** (возможны потери), **exactly-once** (труднодостижимо, требует идемпотентности). ⚠️ Кандидат не знал терминологию.

**C3.5. Poison message и DLQ.** [P4]
- Сообщение падает → возвращается → снова падает: счётчик повторов + лимит (max attempts) → мёртвая очередь (**DLQ**).

**C3.6. Брокер упал — как не потерять сообщения.** [P3]
- В RabbitMQ — флаг **durable/persistent** при создании очереди: сообщения бэкапятся на диск. В Symfony включено по умолчанию.
- Платёжная система с polling: ретраи с паузами + **DLQ** — «задержка оплат (плохо, но не критично) вместо потери (критично)».

# Часть D. Инфраструктура

## D1. Контейнеризация и оркестрация

**D1.1. VM vs контейнер.** [G2, G6, P5]
- **Виртуализация**: гипервизор эмулирует машину (своя ОС поверх твоей) — тяжело, но **изолировано по-настоящему**.
- **Контейнер**: использует ОС хоста, сисколы почти напрямую — лёгкий, быстрый, **изоляция слабее**.
- Плюсы Docker: лёгкость, образы **слоями** (пересобирается только изменённый слой), Docker Hub, быстрый деплой/скейлинг. Провокация «подозрительный бинарник»: в контейнере рискуешь основной ОС (изоляция неполная) [G6].

**D1.2. Docker vs Kubernetes.** [G2, P5]
- Docker — создание контейнеров/образов; K8s — **оркестрация**: self-healing, распределение нагрузки, rolling-обновления, «чтобы не все поды умерли». Для отказоустойчивости — 3+ ноды.

## D2. Git

**D2.1. merge vs rebase.** [P4]
- `merge` — обычное слияние, **сохраняет историю**. `rebase` — **переписывает историю** (можно потерять коммиты); допустим при одиночной работе в ветке, в команде — лучше merge.

## D3. Observability: мониторинг, алертинг, трейсинг

**D3.1. Инструменты.** [G6] — **Prometheus** (метрики/time series), **Grafana** (дашборды/алерты), **Jaeger/Tempo** (бэкенды распределённой трассировки), **OpenTelemetry** (стандарт телеметрии: API+SDK, экспорт по **OTLP**), **ELK/Loki** (логи). Шпаргалка: метрики — «сколько», логи — «что», трейсы — «где».

**D3.2. Алертинг сервиса.** [G6] — доля ошибок выше порога (4xx — Bad Request, 401/403 — авторизация; connection refused — проблема инфраструктуры), CPU/память выше порога.

**D3.3. Что такое распределённая трассировка и зачем.** [✍️]
- В микросервисах запрос проходит несколько сервисов; логи каждого по отдельности не дают картину пути — **трейс** связывает все куски в одну историю.
- Понятия: **trace** — история одного логического запроса; **span** — отрезок пути (сервис, вызов БД, внешний API); **trace ID** — общий идентификатор; **span ID + parent/child** — дерево спанов.
- Главный юскейс: за минуты найти, **какой сервис** добавил задержку или уронил запрос (каскадные таймауты, ретраи), расследовать инцидент по одному ID.

**D3.4. Как контекст пробрасывается между сервисами (propagation).** [✍️]
- Сервис читает контекст из входящего вызова, создаёт **child span**, передаёт контекст дальше при каждом исходящем вызове.
- HTTP — **W3C Trace Context**: заголовок `traceparent` (`{trace-id}-{span-id}-{flags}`); старый стандарт — X-B3 (Zipkin). gRPC — metadata. Kafka/RabbitMQ — **заголовки сообщения** (воркер продолжает трейс родителя, а не начинает новый).
- «Трейс оборвался» = почти всегда **заголовок не проброшен**: самописный HTTP-клиент без middleware, несовместимые стандарты между сервисами.

**D3.5. Сэмплинг трейсов.** [✍️]
- Трассировать **каждый** запрос дорого: трафик телеметрии сопоставим с боевым → хранят выборку.
- **Head-based** — доля трафика решается на входе (напр. 5–10%). **Tail-based** — решение после завершения: можно сохранить **все ошибки и медленные** трейсы — то, ради чего всё затевалось.
- Железное правило: **ошибки и хвосты (p99) не сэмплировать**. В платежах — 100% или выборка по бизнес-ключу (все операции с транзакцией — всегда).

**D3.6. OpenTelemetry.** [✍️] 🪤
- Vendor-neutral **стандарт телеметрии**: API (код приложения) + SDK (сбор, сэмплинг, экспорт) + экспортеры по протоколу **OTLP**; три сигнала (traces + metrics + logs) под одним зонтиком.
- Смысл: инструментируешься один раз — отправляешь в любой бэкенд (Jaeger, Tempo, Datadog, New Relic).
- 🪤 Провокация «OTel — это Jaeger»: OTel — API/SDK/протокол; Jaeger/Prometheus — **бэкенды** хранения и UI (карта ловушек №16).

**D3.7. Логи и трейсы: связка.** [✍️]
- **Log correlation**: trace ID пишется в каждый лог (в Go — контекстный логгер; в PHP — Monolog-процессор). По логу/алерту → трейс; по трейсу → логи конкретного спана.
- Без связки трейсинг и логи — два параллельных мира, расследование снова «по времени».

**D3.8. Метрики: RED и USE.** [✍️]
- **RED** — про сервисы и запросы: **R**ate (RPS), **E**rrors (доля ошибок), **D**uration (p50/p95/p99).
- **USE** — про ресурсы: **U**tilization, **S**aturation (очереди, пулы), **E**rrors.
- Расследование: RPS прежний, latency выросла, ошибок нет → ресурсы (USE) или код/БД (трейс). Latency и ошибки растут вместе → внешний сервис/БД — трейс покажет виновного.

**D3.9. SLO / SLI / error budget.** [✍️]
- **SLI** — измеряемая метрика (p99 < 500 мс; доля успешных запросов). **SLO** — целевой порог (99,9%). **Error budget** — допустимый объём нарушений SLO за период.
- Алерт вешают на **скорость сжигания бюджета**, а не на «одну ошибку» — иначе алерт-шум.
- 💡 Для senior хватает связки «SLI → SLO → budget» + чем это лучше алертов на пороги.

**D3.10. «Трейсы пропали» — порядок проверки.** [✍️]
1. **Propagation** — заголовок доходит? (обрыв = не проброшен клиентский вызов).
2. **Сэмплинг** — ошибки и медленные гарантированно пишутся?
3. **Экспорт** — коллектор/бэкенд живы, OTLP-endpoint и токен правильные?
4. **Часы** сервисов синхронизированы (NTP) — иначе спаны «кривым деревом».
5. **Стандарты** propagation между сервисами совместимы (traceparent vs X-B3 не срастутся).

**D3.11. Трейсинг в платежах.** [✍️]
- Денежная операция — сквозной путь: API → валидация → антифрод → внешняя ПС → вебхук → сверка. Трейс = **аудит-ключ**: по `payment_id` в атрибутах спана и тикету саппорта виден весь путь.
- Внешняя ПС обычно не участвует в propagation → спан «external call» + маппинг `payment_id ↔ trace_id` в своих сервисах.
- Ретраи видны: один trace ID, несколько попыток-спанов — сразу видно «промолотило 3 раза перед успехом».

# Часть E. Безопасность (общая)

**E1.1. С какими уязвимостями сталкивался и защита.** [P3]
- **SQL-инъекция** (prepared statements). **XSS** — чужой JS исполняется в браузере жертвы. Перебор уязвимых файлов (`phpinfo()`, конфиги): в публичном доступе — только точка входа, профайлеры на проде отключить. XML/ZIP-бомбы. Открытые порты (сканер nuclei). Повышение привилегий. Отсутствие TLS (сниффинг).

**E1.2. Защита кук: флаги.** [P3] ⚠️
- **`HttpOnly`** — запрещает доступ из JS (`document.cookie`), защита от кражи через XSS. **`Secure`** — только по HTTPS. **`SameSite`**, **`Domain`**.
- ⚠️ Кандидат назвал только SameSite/Domain, пропустил HttpOnly и Secure.

**E1.3. Почему нельзя MD5 для паролей.** [P3] ⚠️
- Быстрые коллизии + **timing attack** (по времени ответа подбираем символ). Нужны современные алгоритмы с **солью**: bcrypt/argon2id. MD5 подбирается за час, современный — ~10 лет.

**E1.4. JWT: что это и зачем.** [P3]
- JSON Web Token — метод авторизации наравне с сессиями; нужен в **распределённых системах** (несколько серверов, сессии не шарить). Три части через точку (base64): header, payload, signature.

# Часть F. Алгоритмы

**F1.1. Разворот массива (задача с багом).** [P5] 🪤 🔧
- Функция с багом: цикл по **всем N**, а не по **N/2** → массив разворачивается дважды и возвращается в исходный порядок.
```php
// Багнутая версия: цикл по всем N → разворачивает дважды
function reverseArray(array $array): array
{
    $temp = 0;
    for ($i = 0; $i < count($array); $i++) {
        $temp = $array[$i];
        $array[$i] = $array[count($array) - $i - 1];
        $array[count($array) - $i - 1] = $temp;
    }
    return $array;
}
```
- Для `[1,2,3,4,5,6]` результат — снова `[1,2,3,4,5,6]`. Фикс: `$i < intdiv(count($array), 2)`.
- На практике — **`array_reverse()`** (в Go — писать руками через два указателя), не изобретать велосипед. ⚠️ Кандидат ошибся в ручной трассировке индексов (считал «от единицы», а не от нуля).

# Часть H. Приёмы на собеседовании (фидбек интервьюеров)

> Из go-банка (Часть E). Не вопросы, а поведение, которое решает исход.

1. **Проговаривай вслух** — молчание в 2026-м = подозрение на нейронку/гуглёж; лайвкод — мини-лекция [G5].
2. **Подводи итоги**, если ответ затягивается — «каша в голове» интервьюера станет твоей проблемой [G5].
3. **Уточняй требования до кода** (число реплик, таймауты, регистр) — большинство ставит плюсик [G7, G3].
4. **Прогоняй примитивный кейс до «я сделал»** — сам нашёл ошибку до заявления о готовности — ещё лучше [G7].
5. **Декомпозируй** — функция >50 строк → выноси [G7].
6. **Честное «не знаю/не доводилось» — ок** (администрирование Kafka/БД): интервьюер проверяет глубину и честность [G1, G3, G6].
7. **Синьорность = решать в ограничениях** («нельзя Redis»), не плодить технологии [G5].
8. **Ты можешь оказаться правее интервьюера** (кэш: O(1) против O(n)) — собеседование middle/senior — рассуждение, не диктант [G5].
9. **Терминология до автоматизма** (JOIN, HAVING/WHERE, уровни изоляции, селективность) — «решил задачи» ≠ «прошёл собеседование» [G3].
10. **Вопросы кандидата** — по делу, не перегружать: состав команды, роль лида, соседние команды; на ранних этапах конкретику о задачах не выпытывать [G1, G3].
11. **Связывай свой опыт с проектом интервьюера** («сейчас в похожей истории») — работает [G1].
12. **Код-ревью на собесе** может быть жёстче, чем в жизни, — это нормально [G1].
